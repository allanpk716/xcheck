# xcheck 反馈分级(Triage)设计文档

> **文档性质**:在现有 `/xcheck`(diag/review)fan-out 汇总流程之后,**新增第 6 步:反馈分级**——把多家 agent 的反馈逐条按"可验证性"分成三类。本设计不改动现有第 1~5 步。
> **范围**:仅新增 `prompts/triage.md` + 在 `lib/flow.md` 末尾追加第 6 步。不改 agent 检测、不改 subagent 搬运、不改第 5 步汇总。
> **日期**:2026-08-13

---

## 0. 一句话定位

第 5 步主会话做完"共识/分歧/存疑"汇总后,**同一个主会话**继续把所有 agent 的反馈**逐条**归入三类(可直接证实 / 可设计实验验证 / 存疑仅参考),追加到 `SUMMARY.md`。让用户一眼看出"哪些反馈能直接信、哪些要做实验验、哪些只能参考"。**只设计验证方案,绝不执行。**

---

## 1. 已敲定的设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 第 2 类实验执行 | **只设计不执行** | 保住"只搬运不评判、不自动执行、人拍板"铁律,xcheck 不碰副作用 |
| 验证方案颗粒度 | **轻量**:每条第 2 类出【验证目的 + 一句话方法 + 预期】 | 够用户直接拿去执行,又不让主会话负担过重 |
| 与现有汇总关系 | **新增并存**:保留"共识/分歧/存疑",追加"三类分级" | 既看各家怎么说,又看每条可不可信;信息最全 |
| 由谁做分级 | **主会话连续做**(第 5 步后顺手) | 判断力最强(强模型)、不新增 subagent、最简单 |
| 分级颗粒度 | **逐条**:每家反馈拆成独立问题/建议逐条归类 | 最精准,能看到"这点可证实、那点要实验" |
| 输出形态 | **按类分块**:三类各一个区块,每条标 `[来源]` | 扫读快,同类聚一起;来源标注弥补"同家条目散"的代价 |
| 落点方案 | **方案 B**:独立 `prompts/triage.md`(diag/review 共用)+ flow.md 加第 6 步 | 职责分离,分级逻辑可复用,不与汇总 prompt 耦合 |
| 第 1 类判据行 | **带**:每条第 1 类附一行"判据:可查 X" | 一致性 + 可追溯,看得出归类依据 |

## 2. 三类分级的判定准则

判定对象:**每一条**从各家 agent 反馈里拆出来的独立问题/建议。主会话逐条问自己:"这条能不能被证实?"

### 第 1 类 · 可直接证实(`verifiable`)
> 不用做实验,靠**查/读/对**就能当场判真假。

满足任一即可:
- 能在**代码/配置/日志/文档**里直接查到证据,对一下就知道对错。例:"这里用了 `localStorage` 存 token"——grep 代码就知道。
- 是**事实性陈述**,可被现有信息直接核对。例:"这个函数返回值没判空"——看一眼代码。
- 是**公开可查的常识/规范**。例:"React hook 不能在条件分支里调"。

### 第 2 类 · 可设计实验验证(`empirical`)
> 不能一眼看穿,但能设计一个**轻量实验**来证伪/证实。

满足任一即可:
- 能写个**测试/最小复现**验证行为。例:"这个异步竞态在高并发下会丢数据"——写个并发测试压一下。
- 能靠**运行探测**观察。例:"换 SQLite 会更快"——跑 benchmark 对比。
- 是**性能/可行性**断言,得跑起来才知道。例:"这个方案在 10 万行时卡死"。

每条第 2 类必须配**轻量验证方案**:【验证目的 / 一句话方法 / 预期能证明什么】。**只设计,绝不执行。**

### 第 3 类 · 存疑仅参考(`speculative`)
> 既查不到证据、也没法设计实验验证——主观判断、预测、风格偏好、或信息不足。

满足任一:
- 主观/口味/风格("这个命名不好""这个架构不够优雅")。
- 对**未来/外部**的预测("用户不会喜欢""以后维护成本高")。
- 信息不足,无法判定对错,也设计不出实验。

**默认标注语**:每条第 3 类条目尾部固定加 `⚠️ 未必准确,仅作参考,谨慎采纳`。

### 分类兜底规则
拿不准时**默认往"更不可信"方向兜**:1↔2 模糊归 2;2↔3 模糊归 3。宁可保守标记,不可高估——与"共识≠正确,人拍板"的安全倾向一致。

## 3. 数据流 + flow.md 第 6 步接入

**现有第 1~5 步不动**,只在第 5 步后加第 6 步:

```
第5步:主会话做"共识/分歧/存疑"汇总 → 写 SUMMARY.md   ← 现状,不改
  │
  ▼
第6步:主会话读 triage.md → 把所有 <agent>.summary.md 的反馈逐条三类分级 → 追加到 SUMMARY.md
```

### 第 6 步具体动作(主会话执行)

1. **收集原料**:读 `.xcheck/<ts>/` 下所有 `<agent>.summary.md`(第 4 步已落盘的结构化结论)。**不读 `.raw.out`**(那是噪声留底,分级只看各家自己总结的结构化结论,拆条最稳)。

2. **拆条**:把每家 summary 里的"问题/建议"拆成独立条目,每条记下来源:`[codex] 这里用了 localStorage 存 token`。

3. **套 `triage.md` 模板**:读 `prompts/triage.md`,把 `{{ALL_FEEDBACK}}` 替换成所有条目(带来源标注的拼接)。主会话按模板指令逐条归类。

4. **写盘**:**追加**(不是覆盖)到同一个 `SUMMARY.md`。第 5 步的"共识/分歧/存疑"在前面,第 6 步的"三类验证分级"接在后面,一个文件两段。

5. **收尾**:第 6 步**不**单独再喊一次"你拍板"——第 5 步结尾那句"共识≠正确,你拍板"已覆盖整个 SUMMARY。第 6 步只是给那段话补"可信度依据"。

### 为什么分级的原料是 `<agent>.summary.md`

- 选了"逐条分级",原料必须是**结构化**的,否则主会话没法稳定拆条。
- `.summary.md` 是各家 agent 自己总结的结构化结论(根因/证据/建议 或 裁决/逐条问题/理由),天然条目化,拆条最稳。
- 若某家只有 `.failed.md`(没返回),那家直接不进分级原料,SUMMARY 顶部第 5 步已注明"本轮 N 家未返回",一致。

## 4. `prompts/triage.md` 模板内容

diag 与 review **共用**这一个模板。

```markdown
你是反馈分级者。下面是 N 个**不同** AI agent 对同一个问题/方案各自独立给出的结构化结论(盲评,每家只基于同样 prompt)。

每家结论里包含若干"问题/建议"条目。你的任务:**逐条**判定每条反馈的可验证性,归入下列**三类之一**,然后按指定格式输出。

【各家结构化结论】
{{ALL_FEEDBACK}}

## 三类判据(逐条套)

**第 1 类 · 可直接证实(verifiable)** —— 不用做实验,靠查/读/对就能当场判真假。
满足任一:能在代码/配置/日志/文档里直接查到证据;是事实性陈述可被现有信息核对;是公开可查的常识/规范。

**第 2 类 · 可设计实验验证(empirical)** —— 不能一眼看穿,但能设计轻量实验证伪/证实。
满足任一:能写测试/最小复现验证行为;能靠运行探测观察;是性能/可行性断言得跑起来才知道。

**第 3 类 · 存疑仅参考(speculative)** —— 既查不到证据、也没法设计实验验证。
主观/口味/风格;对未来/外部的预测;信息不足无法判定对错也设计不出实验。

**分类兜底规则**:拿不准时**默认往"更不可信"方向兜**——1↔2 模糊归 2;2↔3 模糊归 3。宁可保守标记,不可高估。

## 输出格式(严格遵守)

按**三个区块**输出,每个区块一个二级标题。每家 agent 的条目用 `[来源]` 标注。

### 第一类 · 可直接证实
> 这些不用做实验,查/读/对一下就能判。可优先据信。

- `[来源]` 反馈内容原句(或紧缩转述)
  - 判据:一句话说明为什么算可证实(可查 X 处 / 是事实 Y)
- `[来源]` …
  - 判据:…

### 第二类 · 可设计实验验证
> 这些不能一眼看穿,但下面的实验能证伪/证实。**仅设计方案,绝不执行。**

- `[来源]` 反馈内容原句(或紧缩转述)
  - 验证目的:这条要证实/证伪什么
  - 方法(一句话):怎么测(如"写个并发测试压 X"、"跑 benchmark 对比 Y")
  - 预期:结果如何则证明该反馈成立 / 不成立
- `[来源]` …
  - 验证目的:…
  - 方法(一句话):…
  - 预期:…

### 第三类 · 存疑 · 仅作参考
> 这些既查不到证据也设计不出实验,未必准确,**谨慎采纳,仅作参考**。

- `[来源]` 反馈内容原句(或紧缩转述) ⚠️ 未必准确,仅作参考,谨慎采纳
- `[来源]` … ⚠️ 未必准确,仅作参考,谨慎采纳

## 铁律

- **逐条判定,不可漏条**——每家每条都要落到一个类。某条实在无法判定,归第 3 类。
- **来源不可丢**——每条必须标 `[来源]`,用户要能追溯是哪家说的。
- **第 2 类只设计方案,绝不执行**(不写"我去跑一下"、不真的调用任何工具去测)。
- **第 3 类必带** ⚠️ 标注。
- 严禁捏造任何 agent 没说过的条目;某家无结论就跳过那家,不要补条。
```

### 输出格式设计理由

- **三个区块对应"按类分块"**——一眼分出"可放心信 / 要做实验验 / 只能参考"。
- **第 1 类给一行"判据"**——这类一眼能查,标清"去哪查"即可,不啰嗦。
- **第 2 类三段式**(目的/方法/预期)——对应"轻量:一句话方法+预期",结构固定好填。
- **第 3 类一行 + 固定 ⚠️**——不值得展开,视觉弱化。
- **`[来源]` 贯穿三类**——虽按类分块(同家条目会散),但每条标来源,想追溯随时能找到是哪家说的,弥补"散"的代价。

## 5. 边界与异常处理

| 异常情况 | 处理 |
|---|---|
| **某家 `.summary.md` 不存在**(只回 `.failed.md` 或超时) | 跳过那家,不进分级原料。SUMMARY 顶部第 5 步已注明"本轮 N 家未返回",一致。 |
| **某家 summary 无可拆条目**(如只回"LGTM,无意见") | 该家不贡献条目,三类区块都不出现它的来源。**不强行补条**。 |
| **三类全空**(所有家 LGTM 或全失败) | 第 6 步输出一行:`本轮无可分级反馈(各家均未提出问题/建议)。` 不输出三个空区块。 |
| **全部条目落同一类** | 正常输出那个类,其余两类各留一行:`第二类:无。`/`第三类:无。`——**不省略空类**,保持三区块结构完整,免得误以为漏了。 |
| **第 2 类某条设计不出实验**(已归第 2 类但实验设计不出来) | **降级到第 3 类**,带 ⚠️。验不了就别假装能验。**注意区分**:这条针对"本来想归第 2 类却设计不出实验";模板铁律里"某条实在无法判定归第 3 类"针对"三类都判不了"——两者归宿相同(第 3 类)但触发点不同,实现时按触发点理解即可。 |
| **条目重复**(两家说本质相同的问题) | **各自保留、各自标注来源**,不合并。来源不同本身就是信息(多家共识=更强信号),合并会丢这个信号。措辞相似但分到不同类的条目也保留——可能可验证性不同。 |
| **第 2 类实验方案写太重**(开始堆命令/脚本) | `triage.md` 铁律已限死"一句话方法"。若主会话仍写重,属 prompt 执行偏差,不在设计层兜底——靠模板约束,不额外加机制。 |
| **用户想重跑/调整分级** | 本设计**不提供**重跑入口(那是未选的方案 C 的能力)。要调只能新开会话重跑整个 xcheck。 |

### 容错:第 6 步失败不影响第 5 步

第 5 步的 SUMMARY **永远先落盘**(共识/分歧/存疑已写进文件),第 6 步是"追加"。即使第 6 步崩了,`SUMMARY.md` 里至少有第 5 步的完整汇总——分级是锦上添花,不是地基,崩了不能把已有汇总也带走。这与 flow.md 现有"一个 agent 挂了不影响其它家综合"的容错风格一致。
