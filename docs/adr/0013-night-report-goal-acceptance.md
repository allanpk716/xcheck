# 夜链终局交付改目标验收单:夜里全自动开发,晨报回答"你的目标实现了没有"

night 定位重申(用户 2026-10-05 拍板):`--night` = 全自动把讨论好的开发完毕——多 agent 评审提完意见自动消化继续开发,夜里不留决策等用户;有问题从开发过程与暂停清单里看出来。旧晨报四问骨架(评了什么/改了什么/执行了什么/早上要决定什么,0.18 随 ADR 0003 定型)在三轮样稿重写中均被否:四段式"抉择/执行/结果"与"开发结果交付说明"都仍在描述"夜里怎么干的"(过程叙事)或"交付物长什么样"(说明书);用户早上要的是**目标验收**——什么功能、开发出怎么样了、我的目标实现了没有、什么没有做到、是否达到验收标准、哪些需要我测试评估、下一步提醒我应该 PR / 合并打 tag 发布 / 其他只有我能执行的操作;不要泛泛甩 compare 链接让用户自己看代码。

决定(2026-10-05):

1. **晨报骨架 = 目标验收单**:【功能】一句 + 结果行(开发完成 / 未完成(x/y) / 失败收工 + 一句验证状态)+【你的目标实现了没有】逐条对照讨论共识/spec User Story 给 ✅/❌ 判定(全部实现也逐条列——这是"开发完毕"的证明)+【没有做到的】+【是否达到验收标准】(自动验证证据 + **需要用户测试评估的**——自动化验不了的验收项,如真实上游行为、UI 效果)+【下一步:需要你执行的操作】(具体动作与链接)+ 裁定与停靠附录照旧。
2. **对话终局播报 = 晨报的浓缩投影**(结果行 + 没做到/需你测 + 下一步动作 + 晨报路径,≤6 行),取代三段式「夜链结论 / 简报 / 推荐下一步」(ADR 0003 定型)。
3. **"下一步"回归操作提醒**:夜里不留决策(授权范围外按既有契约夜间收工/waiting 暂停),但最后一公里发布动作只能用户做——开 PR / 合并打 tag 发布 / 先人工测试 / 续跑,晨报给具体动作与链接。这不是决策交接(0.28 设计过程中一度误砍该段),是"自动化到此为止,剩余动作清单"。有活动约束仍不可推荐直接合并。
4. **STE 四条硬规则并入播报纪律**(与 0.26.0 零编号、黑话拆开、自包含同权重;即"STE 八成"的实指):一句只说一件事;主动语态、句句有主语;一个东西只叫一个名(跟 CONTEXT 词典);结果句句可核对(数字/链接/路径,禁"基本/大概/差不多")。英文受控词表、动词形态细则、冠词规则不迁移(中文无对应意义)。
5. **不动**:夜链结论四值(保留于通知标题与内部账,晨报正文用人话映射:全绿→开发完成、带停靠完成→开发完成(有留底)、未完成→未完成(x/y)、失败收工→失败收工);第 9 步评审四问与 SUMMARY 五字段(交互审核场景,人在场,停点交付语义不同);机器账(NIGHT/FINDINGS)结构。

## Consequences

- 按 [ADR 0012](0012-night-acceptance-protocol.md) 重验触发条款,本版动晨报格式:七判据⑤同步改为"晨报符合目标验收单体例",真实端到端首验另行执行,不随本条目声明完成。
- 验收样本 `.scratch/delivery-rewrite/样本-新格式交付.md`(全绿/未完成/需人工测试/失败收工四变体)经用户逐段确认后固化,为体例权威。
- 目标判定表的机械来源 = 讨论共识(decisions.md)+ spec User Story + 票验收标准;三者不一致时如实标注差异,不造判定。
